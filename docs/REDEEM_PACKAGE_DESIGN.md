# แบบระบบ Redeem Package และผลรีวิว

วันที่: 28 กันยายน 2026 — แบบระบบและบันทึกผลรีวิวก่อนแก้ไข; ปัจจุบันมี implementation ใน working tree แล้ว แต่ยังไม่ได้ deploy migration/Edge Function หรือเชื่อม native printer

## ข้อกำหนดที่ผู้ใช้ยืนยัน

- แพ็กเกจ 2 รูป, 5 รูป และ Unlimited
- นิยามล่าสุดจากผู้ใช้: 1 รูป = ปริ้น 1 ครั้ง ใช้แทนนิยามนับภาพที่ยืนยันรับเดิม
- ถ่ายใหม่และปรับแต่งก่อนสั่งพิมพ์ได้โดยไม่เสียสิทธิ์
- Unlimited ใช้ได้ภายในวันเดียว
- รหัสใหม่ไม่เกิน 5 ตัวอักษร/ตัวเลข และเน้นกรอกครั้งเดียวระหว่างใช้งานต่อเนื่อง ใช้ไม่ครบกลับมาใช้รหัสเดิมได้

นิยามสำหรับแบบนี้: 1 รูป = งานพิมพ์ที่ลูกค้าสั่งหนึ่งครั้งและสำเร็จ จำนวนภาพในเลย์เอาต์ไม่เกี่ยวกับโควตา เช่น คอลลาจ 4 ภาพพิมพ์หนึ่งครั้งใช้ 1 สิทธิ์ พิมพ์ภาพเดิมอีกครั้งโดยตั้งใจใช้เพิ่มอีก 1 สิทธิ์ แต่การส่งคำขอเดิมซ้ำเพราะเครือข่ายขัดข้องไม่ใช่งานใหม่และต้องไม่หักซ้ำ การดาวน์โหลดไม่ใช้สิทธิ์พิมพ์

จำนวนใบต่อครั้งยังเป็นค่าของแพ็กเกจที่ต้องแสดงให้ลูกค้าเห็นและตรึงไว้ตอนออกบัตร ไม่ให้ลูกค้าเพิ่ม copies ได้เองเพื่อรวมหลายชุดเป็นครั้งเดียว ค่าเริ่มต้นที่เสนอคือใช้จำนวนใบต่อชุดเดิมของตู้ เช่น Receipt เดิม 2 ใบต่อครั้ง; ไม่ตีความว่าผู้ใช้กำหนด 1 ครั้ง = 1 ใบแล้ว

ค่าเริ่มต้นที่เสนอ: Unlimited สิ้นสุดเมื่อถึง 00:00 ของวันถัดจากวันที่เปิดใช้ครั้งแรก ตาม Asia/Bangkok ไม่ใช่ครบ 24 ชั่วโมง ส่วนแพ็กเกจ 2/5 รูปมีวันหมดอายุที่ Admin กำหนดและแสดงก่อนขาย การหมดอายุของรหัสที่ยังไม่เปิดใช้แยกจากวันสิ้นสุดสิทธิ์หลังเปิดใช้

## ขอบเขตการตรวจ

ตรวจไฟล์ใน working tree ซึ่งมีการแก้ไขอื่นค้างอยู่ก่อนงานนี้ และรักษาการแก้ไขเดิมไว้

- เส้นทางหลัก: index.html → home.html → payment.html → layout/capture/retake/template/filter/processing/print และ public/shared.js
- app.html กับ src/ เป็นอีก entry point ที่ build รวมกัน
- src-app/ เป็นอีกโครงการ ไม่ใช่ input ของ Vite config หลัก
- ตรวจ migrations และ Edge Functions ใน supabase/; ยังไม่ได้ยืนยัน schema ที่ deploy จริง, native bridge หรือเครื่องพิมพ์จริง

## สิ่งที่พบ เรียงตามความสำคัญ

### P1: เส้นทางพิมพ์ไม่บังคับใช้สิทธิ์จาก backend

public/shared.js:1171–1211 ส่ง image/copies/printerName ไป /api/direct-print หรือส่ง jobId/dataUrl ไป native bridge โดยไม่มีหลักฐานอนุมัติสิทธิ์จาก server ส่วน vite.config.mjs รับคำสั่งพิมพ์ใน dev server โดยไม่ตรวจ session/entitlement และหน้า layout/capture ไม่มี guard ตรวจ authorization

ผล: ในเส้นทางเว็บ/เครื่องพิมพ์ที่ตรวจ ผู้ที่เปิดหน้าปลายทางหรือเรียก endpoint โดยตรงสามารถข้ามขั้น redeem ได้ การเพิ่มตัวนับใน localStorage ไม่แก้ปัญหานี้ ทั้งนี้ไม่สามารถสรุปพฤติกรรมภายใน native bridge ที่ไม่มีซอร์สในส่วนที่ตรวจได้

แก้: ตรวจสิทธิ์ก่อนอนุมัติงานพิมพ์ และตรวจเจ้าของผลงานเมื่อรับ/ดาวน์โหลด; ให้ printer agent รับเฉพาะงานที่ backend อนุมัติแล้ว ตรวจ kiosk, asset, copies, expiry และ job identity ปิดเส้นทางพิมพ์ตรงที่ข้ามการตรวจสำหรับโหมดขายจริง โหมด event และคำสั่ง test print ต้องได้รับอนุญาตจาก config/admin ที่เชื่อถือได้ด้วย

### P1: Claim สำเร็จแต่คำตอบหาย ทำให้ลูกค้าเสียสิทธิ์

supabase/migrations/20260811104603_phase1_foundation.sql:442–462 ปฏิเสธโค้ดที่ไม่ active และเปลี่ยนเป็น claimed ก่อนลูกค้าถ่ายหรือยืนยันภาพ หาก commit สำเร็จแต่เครือข่ายหลุด การส่งซ้ำจะได้ code_not_active โดยไม่มีเส้นทางกู้ session ผ่าน API ปัจจุบัน การ reset ฝั่ง React ก็ล้าง claim ในหน่วยความจำ

แก้: แยกเปิดใช้บัตรออกจากใช้โควตา พร้อม request_id ที่บันทึกก่อนส่งและส่งซ้ำแล้วได้ผลเดิม มี resume โดยตรวจเจ้าของสิทธิ์/อุปกรณ์ และไม่หักโควตาตอน activate

### P1: งานพิมพ์ล้มเหลวถูกบันทึกว่าสำเร็จ

print.html:1715–1720 เรียก completePrintJob แม้ผลไม่ใช่ completed; completePrintJob หักกระดาษ บันทึก print.confirmed และแสดง Printed ทำให้สถานะ failed/simulator/ambiguous กลายเป็นความสำเร็จ หากนำจุดนี้ไปตัดสิทธิ์จะเรียกเก็บผิด และการ retry อาจพิมพ์ซ้ำเพราะแต่ละครั้งสร้าง jobId ใหม่

แก้: จองโควตาก่อนส่งงานและตัดใช้เมื่อพิมพ์สำเร็จ; งานพิมพ์ใช้ jobId เดิมเมื่อ retry, ผลไม่แน่ชัดต้องคงสิทธิ์ที่จองไว้และรอตรวจสอบก่อนส่งอีกครั้ง ห้าม fallback ไปเครื่องพิมพ์อีกทางเมื่อไม่ทราบว่างานเดิมออกแล้วหรือยัง การส่งเข้า spooler ไม่ใช่หลักฐานว่าได้กระดาษจริง

### P2: โครงสร้างปัจจุบันรองรับหนึ่งโค้ดต่อหนึ่ง session

booth_sessions.entitlement_id เป็น UNIQUE, entitlement มีสถานะ claimed แบบใช้ครั้งเดียว และ booth_packages มี prints_per_set แต่ไม่มี print_limit หรือยอดจอง/ยอดใช้จำนวนครั้งพิมพ์ จึงยังใช้ทำ 2/5/unlimited แบบสะสมไม่ได้

นอกจากนี้ public/shared.js:2550–2554 ส่ง Kiosk.packageId ไป claim และ RPC บังคับให้ตรงกับ package ของโค้ด ทำให้ตู้ที่ตั้งแพ็กเกจ 2 รูปปฏิเสธโค้ดแพ็กเกจ 5 รูปในระบบปัจจุบัน

แก้: server อ่านแพ็กเกจจากรหัสเองและตรวจว่าอยู่ในรายการที่ตู้นี้รองรับ ไม่ใช้ packageId ที่ browser ส่งมาเป็นตัวกำหนดสิทธิ์

### P2: รหัสสั้นและไม่มีการจำกัดการลองในเส้นทาง claim ที่ตรวจ

รูปแบบ AB1234 มีพื้นที่รหัสจำกัด และ redeem-claim ไม่มี rate limit ในซอร์สที่ตรวจ แม้มี device authentication แล้ว ควรจำกัดการลองฝั่ง server ต่ออุปกรณ์และ workspace พร้อมบันทึกเหตุการณ์ผิดปกติ ยังไม่ได้ตรวจว่าโครงสร้างพื้นฐานภายนอกมี rate limit หรือไม่

จุดที่ทำได้ดี: claim ใช้ FOR UPDATE ป้องกันการใช้โค้ดเดียวพร้อมกัน, เก็บ digest แทนรหัสจริง, ตรวจ kiosk/package, มี audit และ RPC จำกัด service_role; migration ใหม่ถอนสิทธิ์ RPC รุ่นเก่าจาก anon/authenticated แล้ว จึงไม่ควรสรุปว่าระบบปัจจุบันเปิด RPC เก่าจากไฟล์ 001 เพียงไฟล์เดียว

## รูปแบบรหัสที่แนะนำ

ใช้รหัสสุ่ม 5 ตัวเหมือนกันทุกแพ็กเกจ เช่น K7M2X พร้อม QR ที่ใส่รหัสเดียวกัน ไม่มี prefix หรือขีด ตัวอย่างนี้เป็นรูปแบบ ไม่ใช่โค้ดใช้งานจริง

- สุ่ม 5 ตัวจากชุด 0123456789ABCDEFGHJKMNPQRSTVWXYZ ด้วยตัวสุ่มสำหรับงานความปลอดภัย โดยสุ่มใหม่ถ้าไม่มีทั้งตัวอักษรและตัวเลข ไม่ใช้ I/L/O/U เพื่อลดความสับสน รหัสสั้นจึงต้องพึ่งการจำกัดการลองฝั่ง server และอุปกรณ์ที่ลงทะเบียน ห้ามใช้เป็นรหัสเปิดดูรูปผ่านเว็บสาธารณะ
- ไม่ฝังจำนวนครั้งพิมพ์ไว้เป็นหลักฐานสิทธิ์ รหัสอ้างถึงข้อมูลใน server การเปลี่ยนข้อความหรือ prefix จึงเพิ่มสิทธิ์ไม่ได้
- บัตรพิมพ์ชื่อแพ็กเกจ จำนวนรูป/Unlimited วันหมดอายุ และเงื่อนไขการพิมพ์ให้เห็นชัด
- normalize ตัวพิมพ์ใหญ่และตัดช่องว่างก่อนตรวจ เก็บ HMAC ฝั่ง server พร้อม key version และบังคับรหัสไม่ซ้ำในขอบเขตตู้ที่กำหนดตลอดอายุข้อมูล ไม่เอารหัสหมดอายุกลับมาออกให้คนใหม่เพราะบัตรเก่าอาจถูกนำมาใช้กับสิทธิ์ใหม่ การหมุน HMAC key ต้องยังตรวจการชนกับรหัสเดิมได้ รหัสที่ชนให้สุ่มใหม่โดยมีจำนวน retry จำกัด
- ตรวจรหัสภายใต้ kiosk scope ที่ได้จาก device authentication ไม่เปิด lookup สาธารณะ จำกัดความถี่และพักการลองหลังผิดซ้ำฝั่ง server โดยไม่ให้ refresh หน้าเว็บล้างข้อจำกัดได้ ตั้งค่าเริ่มต้นเสนอผิด 5 ครั้งใน 60 วินาทีพัก 30 วินาทีต่ออุปกรณ์ พร้อมเพดานรวมระดับ workspace และ audit
- ไม่ใส่รหัสเต็มใน audit, analytics หรือ query string ที่อาจถูกบันทึก; QR scanner ส่งรหัสให้แอปเพื่อส่ง POST
- ต้องปรับ validator ทั้งหน้าเว็บ, React, Edge Function, SQL, code_hint constraint, เครื่องสร้าง/พิมพ์บัตร และ native bridge พร้อมกัน
- ช่องกรอกลูกค้าใหม่รับสูงสุด 5 ตัว หากมีบัตรเก่า AB1234 ที่ออกขายแล้ว ให้ใช้เส้นทางย้ายบัตรโดย Admin แบบตรวจสอบยอดและเพิกถอนรหัสเดิมใน transaction เดียว ไม่เปิดสิทธิ์สองชุด และไม่เพิ่มช่องกรอกหลักให้เกิน 5 ตัว

รหัสเป็นสิทธิ์ของผู้ถือบัตร ผู้ที่ถ่ายรูปบัตรไว้ย่อมใช้แทนได้ หากต้องการห้ามส่งต่อจริงต้องเพิ่มการผูกผู้ใช้/PIN ไม่ควรอ้างว่า QR อย่างเดียวพิสูจน์ตัวเจ้าของได้ รุ่นแรกเสนอให้ผูกตู้เดิมและใช้งานพร้อมกันได้หนึ่ง session ต่อบัตร

## แพ็กเกจและการนับ

| แพ็กเกจ | print_limit (ครั้ง) | การหมดอายุ |
|---|---:|---|
| 2 รูป | 2 | ตามอายุสิทธิ์ที่ระบุบนบัตร |
| 5 รูป | 5 | ตามอายุสิทธิ์ที่ระบุบนบัตร |
| Unlimited วันนี้ | NULL | เที่ยงคืนถัดไปของวันเปิดใช้ เวลาไทย |

ใช้ quota_mode = limited/unlimited คู่กับ constraint: limited ต้องมี print_limit > 0; unlimited ต้องเป็น NULL ไม่ใช้ 999999 แทนไม่จำกัด และยังบันทึกยอดใช้ของ Unlimited เพื่อตรวจสอบย้อนหลัง

Unlimited หมายถึงพิมพ์ได้ไม่จำกัดจำนวนครั้งภายในวันเดียวตามนิยามใหม่ ไม่มีเพดานจำนวนครั้งซ่อนอยู่ แต่ทุกครั้งต้องใช้จำนวนใบต่อครั้งที่แพ็กเกจกำหนด มีงานพิมพ์ที่ยังไม่จบได้ทีละหนึ่งงานต่อบัตร และตรวจอายุสิทธิ์ก่อนอนุมัติงานใหม่

ตัวอย่าง: แพ็กเกจ 5 รูป ถ่าย 4 ภาพลงคอลลาจแล้วพิมพ์ครั้งแรก เหลือ 4 ครั้ง; พิมพ์ผลงานเดิมอีกครั้ง เหลือ 3 ครั้ง; ถ่ายใหม่หรือเปลี่ยนเลย์เอาต์ก่อนพิมพ์ไม่ลดสิทธิ์

## ข้อมูลที่ควรเพิ่ม

1. booth_packages: quota_mode, print_limit, usage_unit=print_job, expiry_policy, timezone และ copies_per_print ที่ตรึงจากจำนวนใบต่อชุดของแพ็กเกจ
2. redeem_entitlements: คงเป็น voucher ที่เปิดใช้ครั้งเดียว และบันทึก package snapshot/version ตอนออกบัตร ป้องกันแก้แพ็กเกจแล้วเปลี่ยนสิทธิ์ลูกค้าเก่า
3. customer_passes: entitlement_id UNIQUE, workspace_id, kiosk scope, package snapshot, activated_at, valid_until, used_prints, reserved_prints และ state; สำหรับ limited ต้องมี used_prints + reserved_prints <= print_limit และทุกยอดไม่ติดลบ
4. booth_sessions: เพิ่ม pass_id เพื่อให้หนึ่ง pass มีหลายรอบถ่าย; ปรับข้อบังคับ mode/entitlement อย่างตั้งใจ รองรับบัตรเก่าโดยไม่ถอด UNIQUE เดิมแล้วเปิดใช้ซ้ำทันที
5. final_assets: ใช้ข้อมูลผลงานและความเป็นเจ้าของที่มีอยู่เชื่อมกับ session/pass; ไม่ต้องมี accepted_photos เพื่อคิดโควตา จำนวนภาพในผลงานไม่ใช่หน่วยเรียกเก็บ
6. print_requests: pass_id, request_id, payload_digest และ job_id; UNIQUE(pass_id, request_id) คำขอเดิมข้อมูลเดิมได้งานเดิม คำขอเดิมข้อมูลใหม่ต้องปฏิเสธ
7. usage_ledger: รายการ reserve/consume/release/refund พร้อม job_id จำนวน เหตุผล และผู้ดำเนินการ มี unique constraint ป้องกัน transition เดิมซ้ำ; การคืนสิทธิ์ต้องอ้างงานเดิมและไม่เกินยอดที่จอง/ใช้ ห้ามลบประวัติ
8. print_jobs: pass_id, session_id, asset_id, copies_per_print snapshot, authorization expiry และ idempotency key ที่มีอยู่ พร้อมสถานะ reserved/queued/submitted/completed/failed/ambiguous/cancelled และหลักฐานผลพิมพ์; หนึ่งงานสำเร็จคิด 1 สิทธิ์

เปิด RLS และกำหนด grants ให้ชัดในตารางใหม่ ห้าม browser เขียนยอดใช้หรือ ledger โดยตรง ฟังก์ชันสิทธิ์สูงต้องมีสิทธิ์เรียกจำกัดและตรวจ workspace/device binding ภายในเสมอ

## ขั้นตอนใช้งานและ API ที่เสนอ

1. Admin เลือกแพ็กเกจ → สร้างบัตร → พิมพ์ชื่อสิทธิ์กับรหัส/QR
2. ลูกค้าสแกน/กรอก → activate-or-resume(code, request_id) ตรวจอุปกรณ์และอ่าน package จาก server; สร้าง pass ครั้งเดียว หรือคืน pass เดิมที่ยังใช้ได้ ไม่หักรูป
3. แสดง “แพ็กเกจ 5 รูป · พิมพ์ได้อีก 5 ครั้ง” หรือ “Unlimited · พิมพ์ได้ถึงเที่ยงคืนวันนี้” พร้อมวัน/เวลาที่แน่นอนและจำนวนใบต่อครั้ง
4. เลือก layout ที่ตู้รองรับ → ถ่าย → ถ่ายใหม่/เลือกภาพ → preview ไม่จำกัดช่องภาพด้วยยอดครั้งพิมพ์ที่เหลือ
5. ปุ่ม “ยืนยันพิมพ์ · ใช้ 1 สิทธิ์” → reserve-print(pass_id, session_id, asset_id, request_id) โดย server กำหนดจำนวนใบจาก package snapshot
6. Server จองสิทธิ์และคืน job เดิมหรือ job ใหม่ → printer agent ส่งงาน → report-print-result(job_id, result, evidence) ตัดใช้เมื่อยืนยันสำเร็จ หากไม่แน่ชัดแสดง “กำลังตรวจสอบงานพิมพ์” ไม่แสดงว่าสำเร็จ
7. ปุ่มหลัก “ถ่ายต่อ” หากยังมีสิทธิ์; ปุ่มรอง “พักไว้ใช้ต่อ” ล้างรูปและ token บนตู้ ลูกค้ากลับมากรอกบัตรเดิมเพื่อใช้ยอดที่เหลือได้จนหมดอายุ ไม่ต้องออกรหัสใหม่หรือกรอกทุกครั้งที่ถ่ายต่อ

แม้เหลือสิทธิ์ 1 ครั้งก็เลือกเลย์เอาต์ 2/3/4 ภาพได้ตามความสามารถของตู้ เพราะใช้เพียงหนึ่งงานพิมพ์ ปัญหาแพ็กเกจ 5 รูปเหลือภาพสุดท้ายที่ใช้กับ strip ไม่ได้จึงไม่เกิดภายใต้นิยามใหม่

## หน้าจอที่เสนอสำหรับใช้งานจริง

ใช้คำว่า “ครั้งพิมพ์” บอกยอดในหน้าจอเพื่อแยกจากจำนวนภาพในเลย์เอาต์ และแสดงจำนวนใบต่อครั้งจากแพ็กเกจ ไม่ต้องสมัครสมาชิก ตั้ง PIN หรือเลือกราคาอีกหลังกรอกบัตร

| จังหวะ | ข้อความตัวอย่าง | การกระทำ |
|---|---|---|
| หน้าเริ่ม | “กรอกรหัส 5 ตัว หรือสแกน QR” | ช่องเดียว แป้นตัวอักษร/ตัวเลขขนาดใหญ่; กรอกครบเปิดปุ่ม “ใช้สิทธิ์” ให้กดยืนยัน |
| ใช้บัตรครั้งแรก | “แพ็กเกจ 5 ครั้ง · เหลือ 5 ครั้ง” และวันหมดอายุ | “เริ่มถ่าย” |
| กลับมาใช้บัตรเดิม | “ยินดีต้อนรับกลับ · พิมพ์ได้อีก 3 ครั้ง” | “ถ่ายต่อ” ไม่เปิดรูปของรอบเก่าอัตโนมัติ |
| ถ่าย/เลือกแบบ | มุมบน “เหลือ 3 ครั้งพิมพ์” | เลือกแบบ ถ่าย ถ่ายใหม่ได้ |
| ตรวจรูป | “พิมพ์ครั้งนี้ใช้ 1 สิทธิ์” พร้อมจำนวนใบที่จะได้ | “ยืนยันพิมพ์” / “ถ่ายใหม่” |
| กำลังพิมพ์ | “กำลังพิมพ์ กรุณารอ” | ไม่ให้สั่งงานเพิ่มหรือเปลี่ยนบัตรระหว่างงานค้าง |
| พิมพ์สำเร็จ ยังมีสิทธิ์ | “เรียบร้อย! พิมพ์ได้อีก 2 ครั้ง” | ปุ่มใหญ่ “ถ่ายต่อ” และปุ่มรอง “พักไว้ใช้ต่อ” |
| พักไว้ | “เก็บบัตรรหัสเดิมไว้ กลับมาใช้ต่อได้อีก 2 ครั้ง ก่อน [วันหมดอายุ]” | แสดง 5 วินาทีแล้วกลับหน้าเริ่ม ไม่แสดงรหัสเต็มค้างบนตู้ |
| สิทธิ์หมด | “ใช้ครบแล้ว ขอบคุณครับ” | ให้รับรูป/ดาวน์โหลดตามการตั้งค่าตู้ แล้วกลับหน้าเริ่ม |
| Unlimited | “Unlimited · ใช้ได้ถึง [วัน] 23:59 น.” | หลังพิมพ์มี “ถ่ายต่อ” / “พักไว้ใช้ต่อ” เหมือนแพ็กเกจอื่น; backend ตัดสิทธิ์ตรงเที่ยงคืน |

บัตรกระดาษ/QR ที่ได้รับตอนซื้อคือสิ่งที่ลูกค้าเก็บไว้กลับมาใช้ ไม่ต้องจำยอดเอง รหัสไม่เปลี่ยนทุกครั้ง ใช้ไป 2 จาก 5 แล้วกลับมาอีกวันยังเหลือ 3 ถ้าบัตรยังไม่หมดอายุ ส่วน Unlimited กลับมาได้ภายในวันเปิดใช้เท่านั้น

### ออกจากหน้าจออัตโนมัติ แต่ไม่ล้างยอดบัตร

ค่าที่เสนอเพื่อความง่ายในการใช้งาน:

- หลังพิมพ์สำเร็จ หากไม่แตะหน้าจอ 30 วินาที กลับหน้าเริ่มอัตโนมัติ พร้อมนับถอยหลัง “จะพักสิทธิ์ให้อัตโนมัติใน … วินาที”; แตะ “ถ่ายต่อ” ก็ใช้งานต่อได้ทันที
- ระหว่างเลือกแบบ/ถ่าย/แต่ง หากไม่มีการใช้งาน 90 วินาที ให้เตือน 15 วินาทีพร้อมปุ่ม “ยังใช้งานอยู่” ก่อนปิดรอบที่เปิดอยู่; ไม่นับช่วงที่ระบบกำลังนับถอยหลังถ่าย ประมวลผล หรือพิมพ์เป็นการเดินหนี
- เมื่อกดพัก/หมดเวลา ล้าง session credential รูปตัวอย่างและข้อมูลลูกค้าบนตู้ กลับหน้าเริ่ม; ไม่ revoke บัตร ไม่ลบ pass และไม่ลดโควตาที่เหลือ รูปที่ยังไม่ส่งพิมพ์ไม่เสียสิทธิ์และไม่สัญญาว่าจะกู้ร่างเดิมได้
- หากมีงานพิมพ์ค้างหรือผลไม่แน่ชัด ห้ามคืนยอดจองหรือเปิดงานใหม่เพียงเพราะ timeout ให้แสดงสถานะตรวจสอบ/เรียกพนักงาน และซ่อนข้อมูลลูกค้าเมื่อหมดเวลาได้ งานเดิมยังต้องถูกติดตามจาก server/agent
- การ refresh หรือแอปเปิดใหม่ต้องกู้สถานะงานที่ยังค้างก่อนอนุญาตงานถัดไป ไม่เริ่มรอบใหม่แล้วลืมยอดจองเดิม

### ป้องกันสิทธิ์ซ้อนโดยไม่เพิ่มขั้นตอนให้ลูกค้า

- มียอดหนึ่งชุดต่อบัตรใน server ไม่สร้างยอด 5 ใหม่เมื่อกรอกซ้ำหรือเปลี่ยนหน้า
- เปิดการใช้งานบัตรเดียวได้หนึ่ง session ในเวลาเดียวกันและหนึ่งบัตรต่อตู้ในขณะใช้งาน รุ่นแรกบัตรผูกตู้เดิม; ตู้อื่นแสดงว่าใช้กับตู้นี้ไม่ได้ หากอนาคตอนุญาตหลายตู้ยังต้องมี session lock กลาง
- activate-or-resume ล็อก pass และตรวจ active session แบบ atomic; อุปกรณ์เดิมที่มี session token ถูกต้อง resume ได้ ถ้ามีอีก session ใช้งานอยู่ให้แสดง “บัตรนี้กำลังใช้งานอยู่” ไม่ยึดสิทธิ์จากผู้ใช้อีกคนอัตโนมัติ
- session มี lease/token generation ที่ต่ออายุตามการใช้งานจริงและหมดอายุตามการพัก ไม่ต่ออายุไม่สิ้นสุดจากแท็บที่เปิดทิ้งไว้ เมื่อปิด/แทนที่ session ให้คำขอจากแท็บเก่าไม่สามารถจองหรือเริ่มส่งงานใหม่ได้
- การเปลี่ยน session ไม่ยกเลิก print job ที่ส่งแล้ว รายงานผลที่ยืนยันจาก agent ของงานเดิมยังต้องประมวลผลได้ ป้องกันยอดจองค้างจากการ logout
- การพักสิทธิ์กับการจองงานใหม่ต้องตรวจ token generation ภายใน transaction เดียวกัน และต้องมี unique constraint/locking คุม active session ไม่พึ่งปุ่ม disabled อย่างเดียว
- คำขอพิมพ์สองครั้งพร้อมกันหรือ retry ใช้กติกาการจองและ idempotency เดิม กรอกโค้ดซ้ำไม่รีเซ็ตยอด ไม่ต่อวัน Unlimited และไม่หักสิทธิ์
- ผู้ที่รู้รหัสยังถือสิทธิ์แทนกันได้ตามโมเดลบัตรผู้ถือ การกัน session ซ้อนป้องกันใช้พร้อมกัน ไม่ได้พิสูจน์ว่าเป็นคนเดิม ระบบนี้ตั้งใจไม่เพิ่มบัญชี/PIN เพื่อให้ขั้นตอนสั้น

## การจองและตัดสิทธิ์พิมพ์อย่างปลอดภัย

ก่อนยืนยัน เตรียมไฟล์ผลงานที่พิมพ์ได้ให้สำเร็จและตรวจว่าเป็นของ session/pass นี้ รูปที่ถ่ายทิ้งไม่ต้องขึ้น cloud ไม่เชื่อจำนวนใบหรือ asset ของบัตรอื่นที่ browser ส่งมา

ใน transaction สั้นหนึ่งครั้ง:

1. Lock pass row และตรวจอุปกรณ์/workspace/session
2. ตรวจ request_id เดิมก่อน: หาก payload ตรง คืนงานและสถานะเดิม แม้ retry หลังหมดอายุ; ไม่สร้างงานหรืออนุญาตให้พิมพ์ใหม่จากการอ่านสถานะ
3. สำหรับคำขอใหม่ ใช้เวลาของ server หลังได้ lock ตรวจ expiry/revocation, asset และจำนวนใบจาก package snapshot
4. ตรวจว่าไม่มีงานที่ยังไม่จบของบัตรนี้ และสำหรับ limited ต้องมี print_limit - used_prints - reserved_prints >= 1
5. เพิ่ม reserved_prints 1, สร้าง print_job, ลง ledger และบันทึก request ใน transaction เดียว จึงไม่มีช่วงที่สองคำขอแย่งใช้สิทธิ์สุดท้ายได้
6. Commit แล้วค่อยส่งงานผ่าน printer agent ที่ตรวจ authorization และเก็บสถานะ job อย่างถาวร ห้ามรอ printer/network ขณะถือ database lock

เมื่อได้ผลพิมพ์ ใช้ transaction อีกครั้งเพื่อล็อก pass/job ในลำดับเดียวกันทุกเส้นทางและเปลี่ยนสถานะได้ครั้งเดียว:

- completed ที่มีหลักฐานเชื่อถือได้: reserved_prints ลด 1, used_prints เพิ่ม 1 และบันทึก consume; callback ซ้ำไม่ตัดเพิ่ม
- failed/cancelled ที่ยืนยันได้ว่าไม่มีผลงานออกและจะไม่มีงานค้างถูกส่งภายหลัง: reserved_prints ลด 1 และบันทึก release
- submitted/ambiguous/timeout หรือออกเพียงบางใบ: คงยอดจองไว้ ให้ตรวจสอบก่อน ห้ามคืนสิทธิ์อัตโนมัติหรือส่งซ้ำไปอีก transport

งานที่ยังไม่เคยส่งให้ printer agent อาจยกเลิกเมื่อหมดอายุการจองได้ โดยยกเลิก authorization อย่างถาวรพร้อมกันและป้องกัน agent หยิบไปส่งหลังยกเลิก ส่วนงานที่เริ่มส่งแล้วต้องตรวจสอบผลก่อน release เสมอ หากเครื่องพิมพ์ไม่มี acknowledgement หรือ deduplication จะรับประกันพิมพ์กระดาษครั้งเดียวไม่ได้ด้วย API อย่างเดียว ต้องมีขั้นตอนตรวจของจริงโดย Admin พร้อม audit

ลูกค้าสั่งพิมพ์ภาพเดิมเพิ่มโดยตั้งใจใช้ request_id ใหม่และเสียอีก 1 สิทธิ์; การ retry ทางเครือข่ายใช้ request_id/job_id เดิมและไม่ส่งพิมพ์ซ้ำอัตโนมัติ งานทดแทนจากความเสียหายต้องให้ Admin อนุมัติอ้างงานต้นฉบับ ป้องกันคืนสิทธิ์พร้อมให้พิมพ์ทดแทนฟรีซ้ำซ้อน

Unlimited ตรวจเวลาทุกการจองงานใหม่และก่อนเริ่มส่งพิมพ์ โดย authorization ต้องหมดอายุไม่เกิน valid_until เมื่อเวลาเท่ากับ valid_until ถือว่าหมดอายุ งานที่เริ่มส่งก่อนเที่ยงคืนปล่อยให้จบและรายงานผลหลังเที่ยงคืนได้ แต่งานที่ยังไม่ส่งห้ามเริ่มหลังเที่ยงคืน การเริ่มถ่ายก่อนเที่ยงคืนไม่ต่ออายุสิทธิ์ ส่วนดาวน์โหลดผลงานเดิมยังทำได้ภายในอายุการเก็บไฟล์

ช่วง offline อนุญาต preview/retake ใน session ที่เปิดไว้ แต่รุ่นแรกต้องเชื่อมต่อเพื่อตรวจสิทธิ์ก่อนเริ่มส่งงานพิมพ์ ส่วนงานที่ส่งแล้วให้ printer agent บันทึกผลถาวรและ sync ภายหลังตาม job เดิม ไม่สร้างงานใหม่เอง

## แผนเปลี่ยนระบบ

1. แก้การข้าม authorization และสถานะพิมพ์ผิดก่อนต่อระบบขาย
2. เพิ่ม pass, ledger, ยอดจอง/ยอดใช้ และ API งานพิมพ์แบบ idempotent พร้อมทดสอบฐานข้อมูลและ printer agent
3. เพิ่ม snapshot/version และให้ code เป็นตัวเลือกแพ็กเกจบน server
4. เปลี่ยนหน้า redeem/preview/print ให้แสดงครั้งพิมพ์คงเหลือและยืนยันพิมพ์; เพิ่มถ่ายต่อ พิมพ์ภาพเดิมอีกครั้ง และ resume
5. ปรับ Admin ให้สร้างบัตร 2/5/Unlimited และพิมพ์เงื่อนไขตรงกับ snapshot
6. เปิดรหัสใหม่ 5 ตัวแบบมีเวอร์ชันและเส้นทางย้ายบัตรเก่าโดย Admin; อัปเดตทั้งสอง entry point และ bridge
7. เก็บบัตรเก่าเป็น legacy_one_set ตามเงื่อนไขเดิม หากย้ายเข้าระบบใหม่ต้องรักษาสิทธิ์หนึ่งชุดเดิม ไม่แปลง prints_per_set=2 เป็น print_limit=2 เพราะจำนวนใบต่อครั้งกับจำนวนครั้งเป็นคนละหน่วย

## เงื่อนไขทดสอบก่อนเปิดขาย

ผลตรวจปัจจุบัน: `npm run check` ผ่าน โดยมี 21 tests ใน 2 ไฟล์ พร้อม typecheck และ build; โหมดจำลองผ่านการกรอกรหัส 5 ตัว พิมพ์ 1 ครั้ง พักรอบ แล้วกรอกรหัสเดิมพบยอดคงเหลือ 4 จาก 5 ชุดทดสอบเดิมยังไม่ได้ยืนยัน RPC บนฐานข้อมูลหรือ native bridge รายการด้านล่างเป็นเกณฑ์ทดสอบเพิ่มเติมก่อนเปิดขายจริง

- 2 รูป: พิมพ์สำเร็จได้ 2 งาน งานที่สามถูกปฏิเสธ
- 5 รูป: พิมพ์สำเร็จได้ 5 งาน แม้ทุกงานเป็นคอลลาจ 4 ภาพ
- Retake/preview/ปรับแต่ง/ดาวน์โหลด ไม่ลดสิทธิ์พิมพ์
- พิมพ์ผลงานเดิมเพิ่มโดยตั้งใจนับอีก 1; คำขอ retry งานเดิมไม่นับเพิ่ม
- เหลือ 1 ครั้งยังเลือกเลย์เอาต์ 4 ภาพได้; แก้ copies จาก client ต้องไม่เพิ่มจำนวนใบที่ได้รับอนุมัติ
- สองคำขอพร้อมกันเมื่อเหลือ 1 จองได้เพียงงานเดียว
- Response หายหลัง commit แล้ว retry ได้ผลเดิม ไม่หักเพิ่ม; key เดิม payload ใหม่ถูกปฏิเสธ
- เปิดใช้แล้วแอปปิด/idle timeout สามารถ resume ได้โดยโควตาไม่หายและคนถัดไปไม่เห็นรูปเก่า
- กรอกรหัสครั้งเดียว พิมพ์ 2 งาน กดพัก แล้วกรอกรหัสเดิมต้องเหลือ 3 จาก 5 ไม่สร้าง pass ใหม่
- ถ่ายต่อหลังพิมพ์ไม่ต้องกรอกรหัสใหม่; timeout กลับหน้าเริ่มและล้างข้อมูลลูกค้าโดยไม่ล้างยอดบัตร
- สองแท็บเปิดบัตรเดียวกันต้องไม่เกิดสอง active session; token ของรอบที่ปิดแล้วจองงานใหม่ไม่ได้
- คำสั่งพักแข่งกับคำสั่งพิมพ์ต้องได้ผลสอดคล้องกัน ไม่ปล่อยงานจาก session ที่หมดสิทธิ์ และยังรับรายงานผลของงานที่ส่งแล้วได้
- รหัสใหม่ยาว 5 ตัว มีตัวอักษรและตัวเลข ไม่มี prefix; สุ่มชนต้องไม่ทับสิทธิ์เดิมและไม่วนสุ่มไม่สิ้นสุด
- จำกัดการกรอกผิดยังมีผลหลัง refresh และไม่กระทบการรายงานผลของงานที่ส่งแล้ว
- Unlimited ก่อน/ตรง/หลังเที่ยงคืนเวลาไทย รวมกรณีรอ lock ข้ามวัน การแก้นาฬิกา client งานจองก่อนแต่ยังไม่ส่ง และงานส่งแล้วแต่รายงานผลหลังเที่ยงคืน
- package mismatch จาก client ไม่เพิ่มสิทธิ์; kiosk/workspace ผิดถูกปฏิเสธ
- กรอก code ผิดหลายครั้งถูกจำกัดจาก server; revoke ปิดการจองและส่งงานใหม่ได้
- เรียกหน้าพิมพ์/endpoint ตรงหรือแก้ localStorage ไม่ทำให้ได้รับสิทธิ์ใหม่
- เครื่องพิมพ์ failed/ambiguous ไม่ถูกยืนยัน completed และไม่ส่งซ้ำโดยไม่ตรวจสอบ
- failed ที่พิสูจน์ว่าไม่พิมพ์คืนยอดจองได้ครั้งเดียว; timeout/partial print คงยอดจองไว้
- callback completed ซ้ำหรือ callback มาสลับลำดับไม่ consume/release ซ้ำ
- ยกเลิกงานจองแข่งกับ agent เริ่มส่งงานต้องมีผู้ชนะเพียงหนึ่งทาง งานที่ release แล้วต้องส่งพิมพ์ไม่ได้
- agent ปิดหลังส่งเครื่องพิมพ์ก่อนบันทึกผล ต้องกู้เป็น ambiguous ไม่ส่งงานเดิมซ้ำเอง
- บัตรเก่าใช้ตามเงื่อนไขเดิม ไม่มีการแปลงจำนวนใบต่อชุดเป็นจำนวนครั้งพิมพ์
